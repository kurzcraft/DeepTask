# 9.2.8 命令等待与取消恢复审计

## 范围和证据边界

本记录承接现有长会话内存任务，仅处理命令收尾等待与取消入口恢复。不删除历史、不截断模型结果、不为正常长任务增加隐式超时、不终止无关进程。源码路径证据不等于现场灰屏唯一根因；单测不代替运行中编辑器验收。

## 实施前观察

1. TerminalProcess.run 的输出循环已有 shell 结束后的 drain deadline，但跳出循环后仍无界等待 streamIterator.return()。当异步生成器有未完成 next() 时，return() 也可能排队永不完成，因此已有 deadline 不保证收尾返回。
2. 输出循环反复 Promise.race 同一待完成的 shellCompletionDeadline/terminalClosed，每块输出都会注册新 reaction；需要区分本轮最小修复与额外内存重构，不以未经测量的推断发布。
3. ChatView 的取消 watchdog 用 ref 记录 arm 时刻，effect 依赖列表不包含点击代际；再次点击时若所有派生值不变，effect 不一定重新启动。hostMadeProgress 又可能因迟到消息改变时间戳清除取消保护，而 didClickCancel 仍为 true。
4. Task.dispose 释放任务终端的具体中断/释放语义仍须核对，不能把 release 命名当成已发送中断。取消必须只作用于当前任务实际拥有的终端，不能借修复取消扩大进程终止范围。

## 最小方案与验证门槛

- 用真实异步生成器模拟永不完成 next()，在收到明确 shell 结束边界后验证收尾有界、输出原文保留；不得以空闲时长判定长任务完成。
- iterator 清理的拒绝必须被观察，清理等待必须有界且定时器可释放；正常返回不遗留轮询器。
- 取消入口在任务仍运行时保持可操作；独立验证重复取消、迟到消息、会话切换和正常完成，避免定时器误判。
- 核对任务中断是否实际释放执行等待；任何终端中断必须限定已有任务所有权。
- 对相关终端、任务、前端回归及类型检查通过后才重建9.2.8，核验包内与安装文件，普通推送，不移动已有标签。
